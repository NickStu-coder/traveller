# Security model

Traveller uses the installed MIT Sidedoor access library for native individual passwords, persisted sessions, passkeys and recovery codes. A username identifies an account; users do not share a password or select another account's profile. Individual access mode is enforced by `TRAVELLER_AUTH_MODE=individual` in the production stack. Public sign-up is disabled; administrators issue single-use invitations. Recovery codes and local operator recovery reuse the library. Email-based reset requires a separate verified-email flow; do not claim recovery codes are an email reset implementation.

Keep cookie flags and Origin/CSRF validation from the foundation. Passkeys require the configured trusted HTTPS origin. Store secrets through the existing encrypted credential vault and retain its encryption secret across upgrades. Never log credential values. Roles derive from the authenticated principal and authoritative user row, not request data or a profile selector.

Traveller APIs require a current user and scope every row operation by owner. Administrators can inspect system operations through explicit admin routes; normal discovery/history must not mix other users' private profiles. Background commits revalidate profile state and job generation. Nullable legacy anonymous/seed data needs explicit administrator handling, not exposure to members. Legacy delete tokens are not an isolation substitute.

Individual account revocation removes its credentials and sessions, disables its trackers/channels and cancels pending jobs in the shared admission lock. The user row and private owner IDs remain for history retention; they are never converted into global/anonymous records. A disabled account cannot authenticate. Watch Profile deletion is an archive with a recorded revision, not a cascading deletion. Household-wide Community Data opt-in is disabled for individual accounts because it cannot authorize disclosure of another user's searches.

The scraper uses short-lived contexts and no public debugging endpoint. Upstream stealth/fingerprint behavior requires review; Traveller adapters must not solve CAPTCHAs or bypass technical restrictions. Prefer ordinary browser context behavior. Detect blocking, stop requests, back off, and let other sources operate. Restrict source URLs to curated hosts and preserve existing SSRF/redirect validation. Do not fetch arbitrary profile-provided URLs. Browser compromise risk remains even when the container runs as a non-root user; contain privileges and network exposure.

Passwords use the library's hashing/verification rather than custom cryptography. Authentication rate limits persist in access state. Mutation bodies are bounded and validated. Notification transports retain DNS-pinning and SSRF protections; user-controlled destinations cannot target private hosts. HTML/email output escapes untrusted fields.

Before public production use, run the complete lint/typecheck/unit/build gate, database ownership and migration integration tests, browser login/passkey checks behind the DSM proxy, dependency audit and a restored-backup rehearsal. Record actual evidence in `VALIDATION.md`; passing a mocked test does not establish production isolation or source availability.
